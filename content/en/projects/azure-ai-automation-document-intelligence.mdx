## The problem

Teams that try to connect Azure AI services to real operations hit the same walls: many services to orchestrate (Document Intelligence, Blob storage, queues, search and the model), state that has to survive async steps and human approvals, tool calls that crash the agent loop, compliance requirements around GDPR, audit and identity, and no way to tell whether a prompt change made answers better or worse.

This platform is built for construction and manufacturing back offices, where the paperwork is supplier invoices, inspection reports, material certificates and drawing sheets, in English and German.

## What I built

![Dashboard: documents processed, agent runs, pending approvals and LLM cost, with cost per day by module and spend per model](/images/portfolio/azure-ai-dashboard.jpg)

**One view of cost and quality.** Documents processed, agent runs, pending approvals and model spend for the last 14 days, broken down by module and by model.

![A German concrete invoice next to its extracted fields, each field linked to the exact place on the page it came from](/images/portfolio/azure-ai-provenance.jpg)

**Document intelligence with provenance.** The pipeline extracts words with coordinates (PyMuPDF, Azure AI Document Intelligence, or vision OCR for scans), classifies the document and extracts a typed record with structured outputs. Every field quotes its source text, so a reviewer can click a value and see where on the page it came from.

![Validation tab: the line items sum to 9,630.00 but the subtotal says 9,530, so the invoice is flagged for review](/images/portfolio/azure-ai-validation.jpg)

**Rules before booking.** Deterministic checks validate totals, dates and cross-field logic. Here the line items do not add up to the subtotal, so the invoice goes to review instead of into the books.

![Operations agent opening a high-priority ticket for a failed concrete cube test, with each tool call shown](/images/portfolio/azure-ai-agent.jpg)

![Approvals: a send-email action requested by the agent waits for a person to approve or reject it](/images/portfolio/azure-ai-approval.jpg)

**A governed agent.** A tool-calling agent looks up projects, suppliers, purchase orders and tickets and searches the knowledge base. Anything that writes (a ticket, an order status, an e-mail to a supplier) is parked for an approver; the worker executes it after approval and the run resumes. Role-based tool permissions, loop detection, token budgets, tool timeouts, a kill switch and a complete audit log sit around it.

![Trace waterfall of one agent run: model calls, tool calls and the approved action, with time and cost per span](/images/portfolio/azure-ai-trace.jpg)

![Evals: golden-set runs for retrieval, QA and extraction, and a comparison between two prompt and embedding configurations](/images/portfolio/azure-ai-evals.jpg)

**Traced and measured.** Every run is an OpenTelemetry trace with token counts and cost per model call, viewable in the app or in Application Insights. Prompts are versioned and golden sets measure retrieval recall, answer correctness and faithfulness, abstention and extraction accuracy. On the demo data, switching to a multilingual embedding model took QA correctness and abstention accuracy from 0.875 to 1.00; the eval view is what showed the gap.

## How it runs

Local-first: one `docker compose up` runs the API, worker, UI, PostgreSQL with pgvector and Azurite, with no Azure resources needed. The same code deploys to Azure Container Apps with managed identity, Key Vault, Blob and Queue storage, PostgreSQL Flexible Server, Document Intelligence and Log Analytics, all defined in Bicep.
